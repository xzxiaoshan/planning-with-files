# 参考：Manus 上下文工程原则

此技能基于 Manus 的上下文工程原则，Manus 是一家 AI 代理公司，于 2025 年 12 月被 Meta 以 20 亿美元收购。

## Manus 的 6 大原则

### 原则 1：围绕 KV-Cache 设计

> "KV-Cache 命中率是生产级 AI 代理的单一最重要指标。"

**统计数据：**
- 约 100:1 的输入输出 token 比率
- 缓存 token：$0.30/MTok，未缓存：$3/MTok
- 10 倍的成本差异！

**实现：**
- 保持提示词前缀稳定（单个 token 的更改就会使缓存失效）
- 系统提示词中不要有时间戳
- 使上下文仅追加，使用确定性序列化

### 原则 2：掩码，不要删除

不要动态删除工具（会破坏 KV-Cache）。改用 logit 掩码。

**最佳实践：** 使用一致的操作前缀（例如 `browser_`、`shell_`、`file_`）以便于掩码。

### 原则 3：文件系统作为外部内存

> "Markdown 是我在磁盘上的'工作记忆'。"

**公式：**
```
上下文窗口 = 内存（易失、有限）
文件系统 = 磁盘（持久、无限）
```

**压缩必须可恢复：**
- 即使丢弃网页内容也要保留 URL
- 丢弃文档内容时要保留文件路径
- 永远不要丢失指向完整数据的指针

### 原则 4：通过重述来操纵注意力

> "在整个任务过程中创建和更新 todo.md，以将全局计划推入模型的近期注意力范围。"

**问题：** 约 50 次工具调用后，模型会忘记原始目标（"迷失在中间"效应）。

**解决方案：** 在每次决策前重读 `task_plan.md`。目标会出现在注意力窗口中。

```
上下文开头：[原始目标 - 遥远，已被遗忘]
...许多工具调用...
上下文结尾：[最近读取的 task_plan.md - 获得注意力！]
```

### 原则 5：保留错误的内容

> "将错误的转向保留在上下文中。"

**原因：**
- 带有堆栈跟踪的失败操作让模型隐式地更新信念
- 减少错误重复
- 错误恢复是"真正的代理行为的最明显信号之一"

### 原则 6：不要被少示例误导

> "单一性导致脆弱性。"

**问题：** 重复的操作-观察对会导致漂移和幻觉。

**解决方案：** 引入受控的变化：
- 稍微变化措辞
- 不要盲目复制粘贴模式
- 在重复任务时重新校准

## 三种上下文工程策略

基于 Lance Martin 对 Manus 架构的分析。

### 策略 1：上下文缩减

**压缩：**
```
工具调用有两种表示形式：
├── 完整：原始工具内容（存储在文件系统中）
└── 紧凑：仅引用/文件路径

规则：
- 对陈旧（较旧）的工具结果应用压缩
- 保持最近结果完整（以指导下一步决策）
```

**摘要：**
- 当压缩达到收益递减时应用
- 使用完整的工具结果生成
- 创建标准化的摘要对象

### 策略 2：上下文隔离（多代理）

**架构：**
```
┌─────────────────────────────────┐
│         规划代理                 │
│  └─ 将任务分配给子代理           │
├─────────────────────────────────┤
│       知识管理器                 │
│  └─ 审查对话                     │
│  └─ 确定文件系统存储             │
├─────────────────────────────────┤
│      执行器子代理                │
│  └─ 执行分配的任务               │
│  └─ 拥有自己的上下文窗口         │
└─────────────────────────────────┘
```

**关键洞察：** Manus 最初使用 `todo.md` 进行任务规划，但发现约 33% 的操作都用于更新它。后来转变为专门的规划代理调用执行器子代理。

### 策略 3：上下文卸载

**工具设计：**
- 总共使用少于 20 个原子函数
- 将完整结果存储在文件系统中，而不是上下文中
- 使用 `glob` 和 `grep` 进行搜索
- 渐进式披露：仅在需要时加载信息

## 代理循环

Manus 以连续的 7 步循环运行：

```
┌─────────────────────────────────────────┐
│  1. 分析上下文                           │
│     - 理解用户意图                       │
│     - 评估当前状态                       │
│     - 审查最近的观察结果                 │
├─────────────────────────────────────────┤
│  2. 思考                                │
│     - 我应该更新计划吗？                 │
│     - 下一个逻辑操作是什么？             │
│     - 有障碍吗？                         │
├─────────────────────────────────────────┤
│  3. 选择工具                            │
│     - 选择一个工具                       │
│     - 确保参数可用                       │
├─────────────────────────────────────────┤
│  4. 执行操作                            │
│     - 工具在沙箱中运行                   │
├─────────────────────────────────────────┤
│  5. 接收观察结果                        │
│     - 结果追加到上下文中                 │
├─────────────────────────────────────────┤
│  6. 迭代                                │
│     - 返回步骤 1                         │
│     - 持续直到完成                       │
├─────────────────────────────────────────┤
│  7. 交付结果                            │
│     - 将结果发送给用户                   │
│     - 附加所有相关文件                   │
└─────────────────────────────────────────┘
```

## Manus 创建的文件类型

| 文件 | 用途 | 何时创建 | 何时更新 |
|------|---------|--------------|--------------|
| `task_plan.md` | 阶段跟踪、进度 | 任务开始时 | 完成阶段后 |
| `findings.md` | 发现、决策 | 任何发现后 | 查看图片/PDF 后 |
| `progress.md` | 会话日志、已完成内容 | 在断点处 | 整个会话期间 |
| 代码文件 | 实现 | 执行前 | 错误后 |

---

## 关键约束

- **单次操作执行：** 每轮一次工具调用。不并行执行。
- **必须有计划：** 代理必须始终知道：目标、当前阶段、剩余阶段
- **文件即记忆：** 上下文 = 易失。文件系统 = 持久。
- **绝不重复失败：** 如果操作失败，下一个操作必须不同
- **通信是一种工具：** 消息类型：`info`（进度）、`ask`（阻塞）、`result`（终止）
